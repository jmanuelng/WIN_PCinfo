# Selected private tester evaluation

This is the separately approved private evaluation route for selected testers under
[#193](https://github.com/jmanuelng/WIN_PCinfo/issues/193). The
[maintainer decision](https://github.com/jmanuelng/WIN_PCinfo/issues/193#issuecomment-5964595509)
allows each selected tester to consent to the exact existing dedicated public
signing certificate in their own CurrentUser Root and TrustedPublisher stores.
It does not establish anyone's actual consent, trust installation, valid signature
or accepted delivery. Each tester reviews and approves their own setup.

A personal evaluation build has no public publisher, Preview, Supported or public
release claim. The application runs on a Windows 10/11 physical PC or client VM
with an already installed eligible PowerShell runtime. No Azure account or
repository checkout is required for a delivered portable package.

## Receive the fixed package

The maintainer supplies the complete qualified portable package, its exact archive,
launcher and application identities, the exact public signer DER certificate and
its independently confirmed SHA-256 identity and expiry. Only public signer
information accompanies the package. Do not distribute the maintainer's private
certificate/key inventory, provider/key names, private keys, PFX files, credentials,
recipient secrets or real assessment evidence.

The maintainer's exact helper and subsequent primary signing approvals remain
separate; approval never covers unknown future bytes. Follow
[exact-candidate signing and package verification](personal-evaluation-certificates.md#freeze-sign-and-verify-the-portable-candidate).
An unsigned source build is not an ordinary assessment delivery.

## Before the Windows 11 user test

The available Windows 11 PC is approved for user-run validation. A prepared
checklist or an unsigned development build does not establish readiness to run
an assessment. Wait for the maintainer's exact qualified package, verification
record and admitted test session. The current Server engineering host is outside
the live client assessment scope.

Use the [current readiness checkpoint and ordered user test matrix](validation/issue-161-session-packet.md#current-readiness-and-retained-history).
The maintainer fills the final source/archive/launcher/application identities,
private result and evidence destinations, protection/recipient prerequisites and
required approvals before activation. Historical candidate tables are retained
evidence, not instructions to run those bytes.

Qualification for user testing means the current automated gate, applicable GUI
checks, independent source reviews and final artifact verification passed. The
user's actual report, cancellation, recovery, privilege, display and cleanup
checks are still pending. Successful user testing and accepted private delivery
are subsequent outcomes; public Preview qualification/publication remain separate.
No Azure account, developer checkout or test-fixture option is needed for the
delivered package. Complete any disclosed Windows prompts personally.

For your first session, record the package identity privately, verify and launch,
decline once, prepare afresh and run Comprehensive Local Only. Inspect the real
report and close viewing explicitly. Then follow the matrix for separate Cancel
and active-window Close runs, protected reopening, deliberate export/refusal,
recovery and the separately approved connectivity choice. Stop on an integrity
or cleanup failure and retain the protected results and ownership records for
the maintainer; do not guess at cleanup or bypass admission.

## Review and consent to user trust

Trust applies to the signer: other code signed by the same certificate can also
be accepted for the approving user while that trust remains valid. Checksums
identify bytes but do not establish publisher trust. Confirm the supplied public
certificate identity independently before consenting. Stop if it cannot be
confirmed.

Use the tester's ordinary Windows user profile. Privately inventory the exact
pre-existing Root and TrustedPublisher entries. After that tester's explicit
consent, durably record an intent before each store mutation, including the exact
certificate identity, store, whether the entry already exists, approving user and
intended action. Import only that exact public certificate into CurrentUser Root
and CurrentUser TrustedPublisher; immediately record the resulting identity and
read each store back. Pre-existing entries are not owned for rollback.

After interruption, reconcile that inventory against the exact entries before
retry or rollback. Missing inventory, ambiguous ownership or unexplained partial
setup is Blocked; preserve the entries rather than guessing ownership. Do not
create a signing identity for a tester, transfer a private key, trust an encryption
certificate, change execution policy, unblock downloaded files or add LocalMachine
trust. If an alternate administrator or SYSTEM worker cannot validate within this
scope, retain the failure and stop the affected qualification; this procedure
grants no broader trust.

## Verify and evaluate

Compare the final archive SHA-256 with the independently confirmed approved
identity before executing any package script. Extract that complete package into
a private local folder. Compare the exact extracted launcher and application
identities, then require Windows Authenticode Valid and the expected signer for
both PowerShell artifacts. Only then run the passive runtime checks and the
application's package Verify workflow. Keep the governing resources together;
double-click Start-WIN-PCInfo.cmd only after those checks pass.

Begin with Comprehensive Local Assessment and Local Only. Review the Preparation
Summary, decline once to verify collection has not started, then prepare afresh
and explicitly approve a run. The operator responds personally to disclosed
Windows prompts. Missing or denied coverage remains a gap. Microsoft Connectivity
Enabled requires its own disclosed choice and fresh preparation approval.

Real acceptance includes the protected report opening, repeat assessment,
separate Cancel and active-window Close, recovery, privilege boundaries,
protected reopening and safe sharing, keyboard/display checks and calibrated
resource/timing evidence from the full acceptance packet. One successful report,
certificate import or controlled fixture does not prove those checks or
independent tester acceptance. Leave unperformed checks pending.

Keep detailed reports, device/network identities and certificate ownership
records private. Never collect or share credentials, private keys, PFX files or
recovery phrases. Retain protected packages and their opening context/keys while
needed. Plaintext HTML export is a separate warned action. The application does
not initiate tester contact or automatically upload results.

## Retire only owned trust

Before retiring trust, prove an independently trusted usable opening route for
retained protected packages. Record a durable removal intent for each exact trust
entry newly added for this tester. Preserve pre-existing entries, the
maintainer's signing key and all package-dependent encryption keys. Remove only
those owned public trust entries, reopen both stores and prove each exact
thumbprint absent; record the observed results immediately.

Missing ownership or absence proof, interrupted removal or unresolved residue is
CleanupIncomplete and blocks further trust mutation or retry until reconciled.
No subject wildcard or broad store sweep is allowed. Keep the inventory until all
intended absence checks pass. Signing/encryption identity retirement is a separate
owner procedure in the
[retention and removal guide](personal-evaluation-certificates.md#retention-rollback-and-exact-removal);
tester trust retirement never authorizes deleting those keys.
