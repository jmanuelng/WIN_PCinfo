# Stable 2.0.0 supported-device matrix

Status: planned decision contract. This document defines the evidence WIN-PCInfo must have before making Supported claims in Stable `2.0.0`. It does not claim that the application, Stable release, validation environments, or evidence already exist.

The governing decision is [Define the Stable 2.0.0 supported-device matrix](https://github.com/jmanuelng/WIN_PCinfo/issues/34). The exact machine-readable companion is [`2.0.0-supported-device-matrix.json`](./2.0.0-supported-device-matrix.json). Current Microsoft lifecycle, image, management, and virtualization facts are recorded in the [support-matrix research note](../../research/stable-supported-device-matrix-facts.md).

## What “Supported” means

Supported is not a badge for WIN-PCInfo as a whole and does not mean that every Windows device will produce complete evidence.

A Supported claim belongs to:

1. one WIN-PCInfo release;
2. one Product Capability;
3. one Named Validation Scenario; and
4. the current accepted Release Evidence for that exact combination.

Windows 10 and Windows 11 clients may remain **runtime-eligible** even when their exact scenario is Preview or Not yet supported. Independent integrity, safety, runtime, or missing-mechanism conditions can still stop or limit a run.

Microsoft’s Windows lifecycle and WIN-PCInfo’s evidence-backed support state are separate facts. WIN-PCInfo never turns an end-of-support operating system into a Microsoft-supported one.

## Stable Windows baseline

Stable `2.0.0` requires Supported claims on:

- Windows 11 Enterprise;
- non-LTSC servicing;
- x64 architecture; and
- the newest broadly deployable Enterprise feature version for which the project has an Approved Windows Client Baseline when the release candidate freezes.

An Approved Windows Client Baseline is the project’s pristine, generalized Azure Compute Gallery image admitted from an approved Microsoft source before test software, enrollment, credentials, or assessment data are introduced. It is not the same thing as an Azure Marketplace offer.

Windows 11 Enterprise 25H2 x64 is the current planning candidate. The exact feature version and latest available cumulative-update build are frozen and recorded in Release Evidence. A higher version number is not automatically selected, and older or newer versions do not inherit the claim.

### Windows 10

Windows 10 remains runtime-eligible, but it does not block Stable `2.0.0`. Without an approved lawful image source, current patch lane, gallery baseline, and qualifying evidence, its scenarios remain Preview or Not yet supported.

If a later release establishes those prerequisites, it may promote a Windows 10 Enterprise 22H2 x64 scenario while clearly showing Microsoft’s end-of-support or ESU context separately.

### Other editions and architectures

Windows Pro, Education, Home, LTSC, ARM64, x86, other Windows 11 feature versions, and the select-new-device Windows 11 26H1 lane receive no automatic Stable claim. They remain runnable where independent checks permit and can be promoted only through their own evidence closure.

## Three Enterprise Reference Scenarios

Stable requires a useful migration path rather than every possible environment combination.

| Reference scenario | Required state | Why it matters | Normal evidence source |
| --- | --- | --- | --- |
| Unmanaged Baseline | Workgroup or local-account device, unmanaged, Microsoft Defender active | Proves clean discovery and honest absence or non-applicability behavior | Fresh Azure Client VM Validation |
| Traditional Enterprise | Active Directory domain joined, Group Policy managed, genuine third-party antivirus registered | Represents the locally observable migration source | Intentional Field Validation Runs |
| Cloud-managed Enterprise | Microsoft Entra joined, Intune managed, Microsoft Defender active, and MDE onboarded where material | Represents the Microsoft cloud management and security target | Intentional Field Validation Runs |

Hybrid Entra join and Configuration Manager co-management remain runnable but Not yet supported unless a later release obtains their own evidence. They are not silently treated as either Traditional or Cloud-managed Enterprise.

## Avoiding a giant test grid

Every capability declares which scenario dimensions can materially change its behavior or conclusion. Evidence can be reused only when a differing dimension is explicitly non-material.

| Capability group | Stable claim rule |
| --- | --- |
| Lifecycle, evidence, reporting, privacy, documentation, provenance, validation, and release controls | Become release-level Supported obligations whose applicable behavior and gates cover every required reference scenario; they are not repeated as artificial device rows |
| Device, Windows, firmware, TPM, form, power, and battery | Claim only the virtual or physical form actually evidenced |
| Identity, privilege, enrollment, local administrators, and effective policy | Publish separate claims for each materially different Enterprise Reference Scenario |
| Software, security products, user resources, and peripherals | Claim only the product condition, recognition entry, dependency, and device form actually evidenced |
| Network, Microsoft connectivity, DNS, certificate, TLS, and trust | Claim only the product network behavior and enterprise network condition actually evidenced |

A matrix summary with mixed rows says `Mixed` or `Limited` and links the scenario rows. It never displays the strongest row as though it covered the capability everywhere.

## Virtual and physical devices

Fresh generation-2 Trusted Launch Azure clients are required for behavior a virtual machine can establish credibly. They can prove application execution, privilege transitions, local Windows collectors, controlled egress, packaging, reports, and actual managed state when the VM is genuinely connected to the service.

Virtual evidence is never reused for physical firmware, TPM attestation, OEM behavior, battery, peripheral, wireless, biometric, or physical-performance claims.

Hardware-sensitive Stable claims require two distinct Representative Physical Setups:

- one laptop for portable form, battery, firmware, TPM, Secure Boot, and relevant peripherals; and
- one desktop-class device for nonportable form, firmware, TPM, Secure Boot, and relevant peripherals.

User-dependency validation includes bounded representative evidence for a mapped SMB resource, a printer, and a common peripheral. This proves the declared collector path, not universal hardware or vendor compatibility.

## Security-product conditions

The matrix separates control states:

- Microsoft Defender active in the Unmanaged and Cloud-managed scenarios;
- Microsoft Defender for Endpoint onboarded only where its locally observable state is material; and
- a genuine Windows Security Center-registered third-party antivirus in the Traditional scenario, with the actual Defender state recorded rather than assumed.

A broad third-party-antivirus condition needs two distinct non-Microsoft product families in two distinct Field Validation setups. If only one product is evidenced, the release may publish a narrow named-product/version scenario but cannot generalize to every third-party antivirus.

Missing, damaged, or ambiguous security registration is tested for safe, honest handling. It is not presented as a Supported environment.

## Network conditions

The application has two product network behaviors:

- **Local Only** performs no assessment network requests and reports network-dependent coverage honestly.
- **Microsoft Connectivity Enabled** performs only the approved, bounded Microsoft management and security connectivity checks.

Stable evidence covers direct outbound connectivity, Windows-configured proxy behavior, TLS inspection, and blocked or partially reachable Microsoft services. Local collection continues when network checks cannot complete, and WIN-PCInfo never weakens or changes proxy, DNS, TLS, firewall, or other security configuration.

An explicitly authenticated-proxy scenario remains Preview until it is separately validated without collecting or storing credentials.

The Azure validation egress profiles—local-only blocked, restricted, and Full Outbound diagnostic control—are test conditions. Full Outbound is not a third product assessment mode.

## Privilege and locale are universal gates

These requirements apply across the matrix without multiplying every scenario row.

Privilege validation covers:

- a standard launch with one accepted elevation;
- an already-elevated launch without another prompt;
- elevation denial with honest partial coverage; and
- the predefined SYSTEM sub-plan for sources that Windows exposes only in that context.

Language-neutral Execution keeps the product interface English while supporting Windows evidence in any language without parsing translated display text. Stable validation uses:

- English execution in every Enterprise Reference Scenario;
- a real Spanish Enterprise Windows baseline as the primary live non-English run; and
- automated `en-US`, `es-MX`, `tr-TR`, `ja-JP`, and `ar-SA` culture and Unicode fixtures.

This does not claim a translated interface or create a separate support row for every Windows display language.

## Field Validation Runs

The project does not need a permanent Entra, Intune, MDE, Active Directory, or third-party-security lab. The maintainer or an intentional Preview evaluator may perform a Field Validation Run on an authorized real client.

A qualifying field run must:

1. identify the exact candidate or release;
2. follow the published beginner-friendly validation instructions;
3. declare the relevant Windows, device, identity, management, security, network, privilege, and locale conditions;
4. produce only the approved privacy-sanitized attestation;
5. keep the Protected Evidence Package and restricted assessment evidence private; and
6. be deliberately reviewed and accepted as Release Evidence.

Ordinary Preview use, feedback, a successful assessment, or a positive comment never becomes validation evidence automatically. WIN-PCInfo never uploads evidence, displays a post-run validation request, or treats product telemetry as proof. Interested evaluators find the workflow through validation documentation or passive About/Help information.

On an existing managed client, WIN-PCInfo does not enroll, offboard, delete, or modify Entra, Intune, MDE, Group Policy, or security-product state. It cleans only its own local run artifacts. If an operator separately creates a disposable managed test identity or enrollment, that external setup and cleanup remain operator-controlled.

Provider-retained audit, security, billing, or historical records are outside the product cleanup claim. This boundary does not permit an active test endpoint or customer-created management object to be silently abandoned when the validation setup itself created one.

## Evidence thresholds

The previously approved support contract remains authoritative:

- a virtualizable Supported Scenario requires at least three successful fresh-client runs across at least two Validation Rounds;
- a physical or externally managed Supported Scenario requires at least two applicable validations across two distinct setups;
- broad third-party-antivirus wording additionally requires two distinct product families;
- every applicable automated, privacy, security, correctness, evidence-protection, cleanup, provenance, language-neutral, primary-operability, and Product Quality Budget gate passes;
- one required product failure blocks the affected claim; and
- no manual waiver can promote missing, failed, expired, or invalidated evidence.

Current evidence freshness, exact-candidate binding, impact review, invalidation, and final signed-artifact smoke validation remain governed by [Define support tiers and release-evidence thresholds](https://github.com/jmanuelng/WIN_PCinfo/issues/9).

## Stable publication behavior

Stable publication is blocked if any of the three required Enterprise Reference Scenarios lacks the evidence required for its material capability claims. The project can continue publishing Preview releases while field evidence is gathered; no Stable delivery date is promised.

A Stable release may still contain unrelated Preview and Not-yet-supported rows. The public matrix identifies the exact release, artifact, Windows build, scenario dimensions, evidence method, dates, limitations, and claim state without exposing device, person, tenant, organization, network, or infrastructure identifiers or restricted assessment evidence.

A new Windows feature version, cumulative update with relevant impact, runtime, rule, schema, dependency, catalog, security boundary, or supported product condition never inherits a claim automatically. It becomes a candidate, receives impact review and affected revalidation, and appears only in a later release’s frozen matrix.

## Implementation handoff

Implementation must treat this matrix as a release and evidence contract, not as one giant test script. The generated matrix must be derived from frozen capability records, scenario definitions, accepted evidence, and their material dimensions. A human-readable summary must remain beginner-friendly while the machine-readable record preserves exact claim and evidence identities.
