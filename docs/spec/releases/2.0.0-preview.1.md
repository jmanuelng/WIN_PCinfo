# WIN-PCInfo 2.0.0-preview.1 scope

Status: **planned**. This document selects the first public Preview scope; it does not claim that the capabilities are implemented or validated yet.

The governing decision is [Define the first public preview slice](https://github.com/jmanuelng/WIN_PCinfo/issues/11), part of the [WIN-PCInfo v2 product and release specification map](https://github.com/jmanuelng/WIN_PCinfo/issues/1). The machine-readable companion is [`2.0.0-preview.1.json`](./2.0.0-preview.1.json).

## Objective

Prove that WIN-PCInfo can safely produce a comprehensive, reconstruction-ready **Microsoft Zero Trust Migration Baseline** from one Windows 10 or Windows 11 client. The baseline covers device, identity, privilege, policy, security controls, applications, user dependencies, network, trust, and locally observable Microsoft-cloud readiness while clearly separating observed facts, advisory interpretation, coverage limitations, and tenant-side discovery needs.

The baseline is not a compliance audit, tenant assessment, automatic migration plan, or remediation service.

## One assessment profile

Preview.1 provides one **Comprehensive Local Assessment**. It selects every release-enabled single-device assessment capability and automatically includes their dependencies.

There are no focused profiles or advanced capability picker in Preview.1. The Preparation Summary shows the complete resolved scope, required privileges, network behavior, limitations, estimated duration and storage, evidence protection, and cleanup behavior before the operator approves the run.

Device-specific inapplicability, missing sources, security-control restrictions, denied elevation, or unavailable evidence do not silently shrink the profile. They receive explicit coverage and reason codes, while unrelated safe collection continues.

## Effective Policy Assessment

Policy assessment preserves three separate evidence layers:

1. **Applied Policy Evidence** records which Local or Domain Group Policy objects Windows reports as applied, including stable identity and precedence where available.
2. **Configured Policy Signals** record a finite, versioned catalog of locally observable Local Policy, Group Policy, Policy CSP, and security-setting values.
3. **Current Control State** records what the applicable Windows management or security control reports at assessment time.

Preview.1 covers locally observable evidence for:

- applied Local and Domain Group Policy;
- Local Security Policy, including account, lockout, audit, security-option, and user-right settings where safely observable;
- MDM Policy CSP results and bounded GPO-versus-MDM conflict signals;
- Microsoft Defender Antivirus, Firewall, attack-surface reduction, network protection, SmartScreen, and tamper protection;
- BitLocker, Secure Boot, virtualization-based security, and Credential Guard;
- Windows Defender Application Control and AppLocker;
- Windows Update and Windows Update for Business;
- RDP, WinRM, SMBv1, SMB security posture, and selected legacy-authentication configuration.

The product uses release-defined Windows 10 and Windows 11 field catalogs and Windows-native structured APIs, CIM/WMI, registry-backed definitions, and inbox Microsoft modules. Preview.1 does not install LGPO, RSAT/GPMC, PsExec, Windows Features, or another policy tool.

Applied policy, configured signals, and current state are never silently collapsed into one supposed organizational policy. Missing classes, modules, permissions, or build-specific fields become explicit coverage gaps. One endpoint cannot establish tenant intent, every unapplied domain policy, universal source precedence, Intune assignment or compliance, BitLocker recovery escrow, actual legacy-protocol use, or organization-wide compliance; those needs become Tenant-side Discovery Tasks.

## Interpretation

Every selected assessment capability is delivered end to end: approved collection, normalized observations, provenance, coverage, advisory findings, recommendations, and report presentation.

Policy and security findings may use versioned Microsoft security baselines and authoritative Microsoft guidance only when the operating-system, product, and configuration context is known. Missing context produces an `Indeterminate` finding or Tenant-side Discovery Task, never guessed noncompliance.

Preview.1 provides no overall security score, compliance percentage, certification, incident declaration, or automatic remediation.

The deliberately small, release-bundled **Software Recognition Catalog** may conservatively recognize known security, management, VPN, DLP, encryption, remote-support, authentication, browser, patching, backup, and other migration-relevant application families. Unknown or ambiguous software remains ordinary inventory, and catalog evaluation failure never erases that inventory. Recognition states its exact or composite match basis and makes no compatibility, licensing, safety, product-health, support, Intune-readiness, Defender-readiness, or deployment claim.

The public [Software Recognition Catalog governance rulebook](../software-recognition-catalog.md) defines approved sources, data-only matchers, entry lifecycle, contribution and review rules, failure behavior, evidence sensitivity, and release gates. Preview.1 never uses `Win32_Product`, downloads a recognition-catalog update, collects license keys, or inspects arbitrary binaries.

A live check against the changing WinGet source is a separate future **Package Availability** capability, not part of Preview.1 recognition. It requires its own permission, network/privacy, source-agreement, structured-correlation, failure, evidence, and validation contract before it may report a time-bound package candidate for an Intune administrator to investigate.

## Privilege and dependencies

Assessment Preflight and the Preparation Summary run before elevation or collection. All required work is front-loaded.

- One ordinary guided launch may request Windows elevation at most once.
- An already-elevated eligible launch does not request elevation again.
- All approved administrator work executes as one frozen, contiguous privileged plan.
- SYSTEM is used only for predefined evidence sources that Windows exposes only in that context, such as applicable MDM WMI Bridge evidence.
- Elevation denial does not terminate safe standard-user collection; affected scopes become unavailable.
- No arbitrary command channel, later prompt, mid-run download, module installation, Windows Feature enablement, or new authority is allowed.

## Network behavior

The Comprehensive Local Assessment supports two preapproved network behaviors:

- **Microsoft Connectivity Enabled** runs only the versioned DNS, TCP, TLS, and HTTP tests needed for the named Microsoft management and security scenarios.
- **Local Only** performs no assessment network requests and records every network-dependent scope as not attempted or unavailable with guidance.

No assessment network request occurs before approval. Network loss never causes unrelated local collection to stop, and WIN-PCInfo never changes proxy, DNS, TLS, firewall, or other security configuration.

Preview.1 uses proxy and resolver evidence plus bounded DNS, connection, TLS-handshake, certificate-chain, negotiated-protocol, cipher, and HTTP metadata. It does not perform packet capture. TLS inspection is reported as confirmed, suspected, not observed within completed tests, or indeterminate according to the available evidence.

Preview.1 does not authenticate to Microsoft Graph, Intune, Defender XDR, Sentinel, Security Copilot, or Global Secure Access APIs. Required cloud-side facts become explicit Tenant-side Discovery Tasks.

## Sensitive evidence boundaries

- User-resource evidence may include exact mapped-drive, share, printer, port, driver, and ownership details only inside Restricted Diagnostic Evidence. It does not enumerate share contents, documents, print jobs, stored credentials, Wi-Fi keys, or unrelated device serial numbers.
- Certificate evidence is purpose-bound to management, authentication, device identity, code trust, TLS inspection, and service connectivity. Private keys, PFX data, passwords, recovery material, and reusable authentication material are prohibited.
- Software evidence excludes license keys, arbitrary file hashes, binaries, documents, and live reputation queries.
- Public artifacts use separate allowlisted and redacted projections; complete or unredacted assessment evidence is never public.

## Results and private sharing

Every safely completed or recoverable partial run produces the versioned Assessment Record, Portable Definition Subset, self-contained English HTML report, manifest, and applicable attachments inside one encrypted Protected Evidence Package.

The Local Package Protector can open the package. Zero or one Package Recipient may be fixed before collection through a verified Recipient Profile. The Completion Summary includes beginner-friendly Result-sharing Guidance. A deliberately exported unencrypted HTML report remains Restricted Diagnostic Evidence and is available only through the warned Restricted Report Export workflow.

## Runtime and Windows scenarios

WIN-PCInfo requires an externally installed, eligible stable PowerShell 7.6-or-later 7.x runtime. The exact runtime patch allowlist is frozen for the release. WIN-PCInfo never installs, upgrades, downgrades, or repairs PowerShell; an ineligible host returns `NotStarted` with official installation and retry guidance.

WIN-PCInfo remains runtime-eligible on Windows 10 and Windows 11 clients when independent safety checks pass. Preview claims are limited to qualifying, latest-patched, non-LTSC Windows 10 Enterprise x64 and Windows 11 Enterprise x64 scenarios selected from the approved release-time validation baselines.

Other Windows 10/11 editions, builds, architectures, device forms, identity states, management states, and security-product combinations remain runnable but receive only the evidence-backed `Preview` or `Not yet supported` state. `Supported` is reserved for Stable releases. Microsoft lifecycle status is presented separately and never becomes a WIN-PCInfo runtime block or support claim.

Physical firmware, battery, peripheral, externally managed Group Policy/MDM, co-management, and real third-party-security-product scenarios remain `Not yet supported` until qualifying physical, managed, or Community Validation evidence exists.

## Release gate

Publication applies the previously approved security, privacy, lifecycle, evidence, quality, support, architecture, validation, and signing contracts to this exact scope. At minimum:

- every applicable deterministic contract, schema, secret-exclusion, provenance, locale-neutral, report, package, failure, cancellation, and cleanup gate passes;
- three clean full-profile Product Quality Budget measurements pass for the frozen workload;
- at least one qualifying fresh Azure Client VM Validation passes for every claimed Windows 10 and Windows 11 Enterprise x64 Preview scenario;
- validation covers standard launch with one elevation, already-elevated launch, elevation denial with honest partial coverage, and the predefined SYSTEM policy plan;
- both network behaviors pass;
- protected-package creation, local and recipient opening, wrong-context handling, Restricted Report Export, corruption, interruption, viewing cleanup, and stale-run recovery pass;
- multilingual and Unicode fixtures plus non-English Windows execution prove that localized display text is never an automation or evidence identifier;
- failure injection covers deadlines, child-process termination, disk exhaustion, denied sources, unavailable Windows components, malformed evidence, and cleanup;
- every Validation Round ends only after independently verified Zero Round Residue; and
- the exact public artifact receives trust, installation, launch, collection, packaging, opening, and cleanup validation.

Trusted Authenticode signing is the target. The governed Attested Preview fallback is allowed only when Azure Artifact Signing is genuinely unavailable, never merely for convenience.
