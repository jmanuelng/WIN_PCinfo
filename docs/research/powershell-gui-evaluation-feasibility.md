# PowerShell GUI evaluation build: feasibility findings

Checked 2026-09-04 against source revision `6cecce6834a8e6ad3e916c9c3b1ba971d0b58aa5`. Research for [Establish the viable PowerShell GUI and real-assessment path](https://github.com/jmanuelng/WIN_PCinfo/issues/131), under [[Wayfinder] Deliver a useful PowerShell GUI evaluation build](https://github.com/jmanuelng/WIN_PCinfo/issues/130). Recommendations below are decision inputs, not approved scope or evidence of delivery.

## Finding

A PowerShell WPF interface reusing the existing assessment and HTML code is technically credible. A working personal build in two days is an aggressive integration target, not something source inspection can guarantee. The critical path is legitimate real-run admission, live progress/cancellation, and protected report access. Drawing a window is the smaller part.

The full-history review is recorded in [Establish the viable PowerShell GUI and real-assessment path](https://github.com/jmanuelng/WIN_PCinfo/issues/131#issuecomment-5548329405). Original decisions [Define modular architecture and dependency policy](https://github.com/jmanuelng/WIN_PCinfo/issues/10), [Define the Assessment Run lifecycle and operator contract](https://github.com/jmanuelng/WIN_PCinfo/issues/13), [Define assessment evidence, finding, and report contracts](https://github.com/jmanuelng/WIN_PCinfo/issues/14), and [Define measurable product quality budgets](https://github.com/jmanuelng/WIN_PCinfo/issues/15) support a PowerShell engine, beginner preparation, responsive operation, and offline HTML. They did not select WPF or Windows Forms. [[Spec] Implement WIN-PCInfo 2.0.0-preview.1](https://github.com/jmanuelng/WIN_PCinfo/issues/37) narrowed the adapter to guided console and specified Comprehensive Local Assessment. The maintainer's new GUI requirement must explicitly supersede that adapter decision. A smaller profile also changes that assessment contract.

## GUI and launch

Both WPF and Windows Forms assemblies loaded successfully in the inspected PowerShell 7.6.5 process; the thread reported STA. This was a read-only type-loading check, with no window, assessment, or installed dependency. It establishes local availability, not compatibility on every recipient device. Microsoft documents PowerShell 7 support for the two APIs and the current `pwsh -STA` option. [PowerShell team](https://devblogs.microsoft.com/powershell/powershell-7-preview-3/), [pwsh options](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_pwsh?view=powershell-7.6).

| Choice | Repository-specific consequence |
| --- | --- |
| WPF in PowerShell | Recommended: one release-owned XAML window, flexible layout, built-in controls and styles, and a small PowerShell adapter. Fits the requested polished beginner experience without changing language. |
| Windows Forms in PowerShell | Viable fallback if existing team experience makes it substantially faster. A small form is straightforward, but deliberate layout and scaling work are still needed. |

Neither framework makes synchronous collection responsive. Keep the STA UI thread for controls. Run the engine in a separate PowerShell runspace, use `PowerShell.BeginInvoke` and a thread-safe queue for bounded progress objects, and drain it from a UI timer. Do not execute PowerShell scriptblock callbacks on arbitrary pool threads without a runspace. Leave the existing privileged and SYSTEM worker processes supervised by the engine. WPF requires control access on its owning dispatcher; WinForms has an equivalent owning-thread rule. [WPF threading](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/advanced/threading-model), [WinForms thread access](https://learn.microsoft.com/en-us/dotnet/desktop/winforms/controls/how-to-make-thread-safe-calls), [PowerShell asynchronous invocation](https://learn.microsoft.com/en-us/dotnet/api/system.management.automation.powershell.begininvoke?view=powershellsdk-7.4.0).

Recommend a double-clickable launcher/shortcut that resolves one supported installed PowerShell executable and invokes the generated application with explicit `-NoProfile -STA -File` arguments and the future GUI mode. A plain `.ps1` association is not a dependable beginner entry point. The launcher must explain missing runtime or policy rejection visibly; hiding the console must not hide bootstrap failures or publisher prompts. Do not include `-ExecutionPolicy Bypass`, change machine policy, silently unblock downloads, or make the UI elevated by default. PowerShell execution policy and the application's own artifact trust test are separate gates. Group Policy can take precedence over process settings. [Execution policies](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-7.6).

Important gap: `Invoke-AssessmentRun` accepts a `ProgressAdapter` and `CancellationToken`, but the ordinary approved assessment calls `Invoke-DeviceReadinessSlice`, whose current parameters expose neither. Synthetic lifecycle tests therefore do not prove live GUI cancellation or progress. Add event/cancellation plumbing to the actual execution chain. Cancellation must stop scheduling new work, reach supervised workers, and finish required packaging/cleanup; killing the GUI worker is not an adequate implementation. Report stages and elapsed activity honestly rather than inventing time-remaining percentages. These are source findings, not an assertion that the complete integration has been tested.

## Real-run admission: two independent blockers

1. `Test-ApplicationArtifactTrust` requires `Get-AuthenticodeSignature` to return `Valid` with a signer certificate. Ordinary unsigned builds cannot collect. `VerifyAttestation` emits a warning and verification result, then exits; it does not grant subsequent Assessment admission. An embedded digest or synthetic preparation fixture is not a substitute. [Preparation.ps1](../../src/Preparation.ps1), [ApplicationMain.ps1](../../src/ApplicationMain.ps1).
2. `Get-ActivePreparationFacts` unconditionally sets `local-package-protector-available` to false. This remains a blocker even after artifact trust succeeds. Actual package code now wraps and unwraps keys with DPAPI CurrentUser, so the missing readiness integration is concrete and narrower than inventing another encryption system. [Preparation.ps1](../../src/Preparation.ps1), [ProtectedPackage.ps1](../../src/ProtectedPackage.ps1).

Microsoft requires a suitable code-signing certificate and a chain trusted by the receiving computer for trusted script signing. A self-signed development certificate is not automatically trusted; local trust establishment is a separate security change, and test trust must not be advertised as public publisher trust. Signing must be applied to the exact final candidate, with the existing package integrity rules reverified afterward. No usable signing identity or live signing route was established by this research. [Microsoft signing guidance](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_signing?view=powershell-7.6).

The human decision has three factual options:

- Use an already authorized signing route that produces a valid signature on the evaluation machine. This preserves current admission, but availability and elapsed setup time are unverified.
- Explicitly authorize a private development-signing arrangement with narrowly managed test trust. This preserves signature-based admission but needs separate setup approval and must remain a personal evaluation artifact. It cannot be silently imposed on recipients.
- Approve a new, explicitly bounded personal-development admission policy, or complete the attested-preview-to-assessment policy connection. Either is a product/security contract change with dedicated negative tests and honest limited-trust labeling; neither exists today. It must never be a fixture switch, general integrity override, or automatic fallback after a bad signature.

Recommend retaining valid-signature admission if the first option is immediately available. Otherwise choose the personal-build policy explicitly before implementation; no factual research result can make that choice on the maintainer's behalf.

For local protection, recommend a preparation probe that verifies the initiating Windows identity and exercises the actual package key-protection/unprotection functions on random in-memory test bytes, compares the result, zeroes buffers, and fails closed. This must run in the same initiating-user context that will package and view results, with no alternate-admin ownership substitution. DPAPI capability alone does not prove the full ownership and cleanup contract; add meaningful wrong-user, failure, and package round-trip tests. The current preparation comments forbid creating keys or protected files during that phase, so keep the probe in memory and review any implicit platform side effects before adoption. No DPAPI probe or trust-store change was performed in this research. [ProtectedData API](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.protecteddata?view=windowsdesktop-10.0), [local package protection](../../src/ProtectedPackage.ps1).

## Useful scope beyond V1

V1 already gathers machine, TPM, software, policy, network, and identity information. Merely putting those fields in a window would not establish the requested improvement. Existing V2 offers typed evidence, explicit unknown/denied coverage, evidence-linked interpretations and recommendations, secret exclusion, and structured HTML. Candidate early-build value is device/firmware readiness plus identity/enrollment and administrator-exposure findings, showing what was observed, what needs attention, what cannot be concluded, and what the consultant should investigate. These candidates exist in [DeviceReadiness.ps1](../../src/DeviceReadiness.ps1), [FirmwareReadiness.ps1](../../src/FirmwareReadiness.ps1), [IdentityEnrollment.ps1](../../src/IdentityEnrollment.ps1), and [AdministratorExposure.ps1](../../src/AdministratorExposure.ps1); compare [ComputerInfo.ps1](../../ComputerInfo.ps1). Their existence does not prove a successful live combined run.

The shortest code-change route is keeping the existing Comprehensive Local Assessment request and LocalOnly behavior, while prioritizing the GUI/report integration. Its downside is the broad live collector surface and validation cost. The smaller-product route requires a named profile whose enabled outcomes and dependencies are frozen in the preparation definition, request schema/validation, execution selection, report resources, and tests. `Get-DeviceReadinessSliceSelection` currently enables all major slices for nonfixture runs, and HTML title/scope are hard-coded to Comprehensive Local Assessment. A cosmetic rename or treating deliberately omitted work as failed collection is incorrect. [Request schema](../../schemas/assessment-run-request.schema.json), [preparation definition](../spec/releases/2.0.0-preview.1-preparation-plan.json), [report and selection code](../../src/DeviceReadiness.ps1).

Recommendation for the scope decision: begin with the existing profile if an initial legitimate run works; use a deliberately limited device/firmware/identity/administrator profile as the fallback when broader live execution prevents the target. Defer additional connectivity, package-source enrichment, recognition expansion, and new cross-domain logic. Do not claim the smaller profile exists until its dependencies and report contract are correct.

## HTML and handoff

The existing renderer produces self-contained HTML inside the protected package. `Open-EvidenceViewingSession` authenticates and validates the package, materializes only the requested artifact in a restricted temporary boundary, and registers cleanup; `Close-EvidenceViewingSession` removes that boundary. No public ViewReport workflow is currently exposed. A GUI Open report action can reuse these functions and launch the local browser, but browser process exit is not a reliable session-close signal when an existing browser accepts a new tab. Keep an explicit Close report viewing action and cleanup on application exit/recovery. Validate browser behavior rather than claiming cache or forensic erasure guarantees. [ProtectedPackage.ps1](../../src/ProtectedPackage.ps1).

The public `RestrictedReportExport` workflow already exists with explicit warning acknowledgment. A proposed Save HTML for private sharing action should reuse it. HTML is restricted plaintext evidence; export must remain deliberate, never an automatic side effect of completion. Consultant-recipient encryption setup exists separately and adds configuration work. For the personal build, protected local viewing plus optional, warned private HTML export is the smaller proposed handoff, subject to the human scope decision. No upload or automatic sharing is proposed. [ApplicationMain.ps1](../../src/ApplicationMain.ps1), [RecipientSharing.ps1](../../src/RecipientSharing.ps1), [Define assessment evidence, finding, and report contracts](https://github.com/jmanuelng/WIN_PCinfo/issues/14), [Select Protected Evidence Package encryption and recovery mechanism](https://github.com/jmanuelng/WIN_PCinfo/issues/30).

## Sequence, uncertainty, and acceptance

1. Settle the exact personal trust route and scope; fix the two admission blockers with targeted negative tests. First prove actual local packaging and opening with no fixtures.
2. Add the PowerShell GUI request/preparation adapter, STA launch, worker runspace, and visible bootstrap errors. Wire real progress and cancel through the live collection path.
3. Connect completion to protected HTML viewing and the agreed deliberate export. Verify failures, partial results, cancellation, cleanup, keyboard access, and the selected screen/scaling cases.

Planning estimate: roughly two focused engineering days if signing is already usable and the existing live collectors work; otherwise the target is at substantial risk. Trust setup and live integration defects can dominate elapsed time. A synthetic GUI demonstration may help decide the experience but does not satisfy the real-assessment target.

Acceptance for the maintainer's exact candidate: from an extracted package, double-click the launcher without entering commands; see understandable scope and preparation; approve once; remain able to move/use the window throughout collection; receive honest completion with no raw JSON; deliberately open the offline HTML and find at least one evidence-backed advisory interpretation plus explicit coverage limits beyond V1's raw inventory; close viewing and verify cleanup. Separately cancel an actual run and confirm workers stop and cleanup/partial-package disposition is accurate. Declining preparation must collect nothing. Invalid trust, wrong-user package access, and package corruption must fail safely and explain what to do. Private HTML export, if selected, requires the explicit warning and destination action. Keep real assessment evidence private; publish only sanitized pass/fail observations.

Environment caveat: two `pwsh` applications resolve on PATH here. The default `[string] $PowerShellPath = (Get-Command pwsh -CommandType Application).Source` in [TestHarness.ps1](../../tests/TestHarness.ps1) can produce an array-binding failure before a test reaches the application. The parent investigation reproduced this and passed the affected test with process-local PATH filtering. Prefer an explicit executable in focused checks and correct the harness resolver during implementation. Do not mistake that failure for a collector defect. This research did not run the full suite or collect real device evidence.
